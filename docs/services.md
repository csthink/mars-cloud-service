# 服务清单与职责边界

本仓的每个模块都是一个**可独立启动的应用**。模块边界由三条规则判定：

1. **按可部署性切**：能自己启动的放本仓，只出 jar 的放框架仓
2. **按消费者数量切**：第一个消费者出现时写在业务服务里，**第二个真实消费者出现**才下沉到框架
3. **依赖单向**：服务 → 框架。**服务之间不加编译期依赖**，只走 HTTP

## 服务划分

### mars-cloud-gateway（8100，错误码 63000–63999）

- 南北向唯一入口；东西向流量不经网关
- 响应式栈：依赖 `mars-cloud-common` 的信封与错误码契约，**不引入 Servlet 栈的 mvc starter**
- 职责：路由、鉴权第一道、全局限流、灰度

### mars-cloud-auth-service（8101，错误码 64000–64999）

认证（AuthN）的**签发侧**：

- 令牌签发与公钥发布（JWKS 端点）
- 登录渠道：微信、企业微信、钉钉、飞书、短信验证码
- 账号、凭据、绑定关系、登录审计

### mars-cloud-upms-service（8102，错误码 65000–65999）✅ 已落地

授权（AuthZ）的**决策侧**（PDP）：

- 输入 subject / action / resource，输出允许或拒绝
- 端点 `POST /upms/v1/decision`；`deny` 是 HTTP 200 的成功决策，只有服务态错误才走非 200
- 当前阶段：决策真相来源是**内存快照**，local profile 启动时发布一份开发种子快照；
  权限数据与角色模型的持久化、注册中心接入属后续阶段
- 细节见 [模块 README](../mars-cloud-upms-service/README.md)

### 业务服务（8104+，错误码 66000+）

按业务域新建，每个服务占 1000 或 2000 一段错误码。

## 两条不可越过的边界

### 认证与授权不合并

认证回答「你是谁」，授权回答「你能干什么」。两者是两个服务、两套模型，
合并会同时放大故障域与权限模型的复杂度。

### 登录渠道返回的组织与角色不参与鉴权

第三方渠道在免登时会顺带返回部门与角色。这些信息**只用于身份确认**，
必须映射进授权服务的主体模型后由 PDP 统一判定，不能直接当成权限事实来源——
否则会分裂出两套权限模型。

## 令牌里不放权限清单

令牌只承载身份。权限每次向授权服务实时查询，这样：

- 改一个用户的权限立即生效，不用等令牌过期
- 权限判定始终有唯一事实来源

即使将来更换认证实现，验证侧也只需改一行 issuer 配置。

## 服务间调用

服务之间的调用**绕过网关**，因此每个服务都要自己完成鉴权，网关只是第一道。
调用时需要透传的上下文（链路标识、调用方身份、租户）由框架的调用组件统一处理。
