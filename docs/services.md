# 服务清单与职责边界

本仓的每个模块都是一个**可独立启动的应用**。模块边界由三条规则判定：

1. **按可部署性切**：能自己启动的放本仓，只出 jar 的放框架仓
2. **按消费者数量切**：第一个消费者出现时写在业务服务里，**第二个真实消费者出现**才下沉到框架
3. **依赖单向**：服务 → 框架。**服务之间不加编译期依赖**，只走 HTTP

## 服务划分

### mars-cloud-gateway（8100，错误码 63000–63999）✅ 已落地

- 系统外部请求统一经过 gateway；服务之间直接调用，不经过 gateway
- 响应式栈：依赖 `mars-cloud-common` 的信封与错误码契约，**不引入 Servlet 栈的 mvc starter**；
  统一响应与异常处理在网关内为响应式栈单独实现，网关自产错误与业务服务返回同一种信封，
  业务服务的响应原样透传
- 路由**显式声明**（当前：`/upms/**` → `lb://mars-cloud-upms-service`、`/sample/**` → `lb://mars-cloud-sample-service`），不开 discovery locator
- 已占用的错误码：`63001`（无匹配路由）、`63002`（目标服务无可用实例）、`63003`（连接目标失败）、
  `63004`（目标响应超时）
- 职责规划：路由 ✅；鉴权第一道、全局限流、灰度待后续接入
- 管理端口 9100（见下节「管理端口」）
- 细节见 [模块 README](../mars-cloud-gateway/README.md)

### mars-cloud-auth-service（8101，错误码 64000–64999）

认证（AuthN）的**签发侧**：

- 令牌签发与公钥发布（JWKS 端点）
- 登录渠道：微信、企业微信、钉钉、飞书、短信验证码
- 账号、凭据、绑定关系、登录审计
- 管理端口 9101（见下节「管理端口」）

### mars-cloud-upms-service（8102，错误码 65000–65999）✅ 已落地

授权（AuthZ）的**决策侧**（PDP）：

- 输入 subject / action / resource，输出允许或拒绝
- 端点 `POST /upms/v1/decision`；已认证请求的 `caller_id` 必须等于令牌 subject。
  `deny` 是 HTTP 200 的成功决策；认证或主体不符返回 401 / 403，服务错误使用对应的非 200 状态
- 当前阶段：决策真相来源是**内存快照**，local profile 启动时发布一份开发种子快照；
  已接入 Nacos 注册中心与两层动态配置；权限数据与角色模型的持久化仍属后续阶段
- 管理端口 9102（见下节「管理端口」）
- 细节见 [模块 README](../mars-cloud-upms-service/README.md)

### 业务服务（8104–8179，错误码 66000–99999）

按业务域新建。业务端口在 **8104 到 8179** 之间挑，对应的管理端口落在 9104 到 9179；
8180 到 8199 留给不承载业务的部署物（当前是 `mars-cloud-monitor` 的 8190）。
所有业务服务共用框架分配表里的 `business` 区段（66000–99999），
各自声明一段、互不重叠——**在下面这张已占用清单里挑一段空白的**，挑重了启动会失败：

| 区段 | 占用者 |
| --- | --- |
| `66100–66199` | `mars-cloud-sample-service`（框架使用示例） |

新建业务服务时，在 `config/application.yml` 的 `mars.error-code.ranges` 声明本服务区段，
并把占用情况登记回上表。区间越界或重叠会在**启动期**报错，不会拖到运行期。

### mars-cloud-sample-service（8103，错误码 66100–66199）✅ 已落地

框架的**使用示例**：一个最小的服务，演示统一响应信封、异常映射、错误码区间与 i18n 的接线。
它不是业务服务，而是可运行的文档——参与构建与测试，所以文档里写的每条行为都有测试钉住。

- 端点 `GET /sample/v1/orders/{id}`、`POST /sample/v1/orders`、`GET /sample/v1/orders/missing`
  （最后一个是**故意返回 404 的演示端点**，用于演示异常映射，不是查询接口）
- 端点 `POST /sample/v1/upms/decision` 经 Nacos 服务名调用 UPMS，不经过网关
- 依赖 mvc、Nacos 与 Feign starter，**无数据库、无 Redis**
- 对 UPMS 只声明本地 Feign 接口与本地 DTO，不增加 service 之间的 Maven 依赖
- 自带端到端验收脚本 `verify-e2e.sh`
- 自带服务调用验收脚本 `verify-feign-e2e.sh`，验证 UPMS 可用和停止后的两条路径
- 管理端口 9103（见下节「管理端口」）
- 细节见 [模块 README](../mars-cloud-sample-service/README.md)

### mars-cloud-monitor（8190，无错误码段）

运行中实例的监控面板，不承载业务。**尚未落地**，本节先登记端口与边界，避免后续新建服务挑到同一端口：

- 经注册中心发现实例，被监控的服务不装客户端、不主动注册
- 只绑内网地址，不经网关，也不在网关路由表里
- 自带表单登录；读取各实例管理端点所需的凭据由部署时的环境变量提供

## 管理端口

每个 Java 服务除业务端口外另有一个管理端口，取值为**业务端口加 1000**：

| 服务 | 业务端口 | 管理端口 |
| --- | --- | --- |
| `mars-cloud-gateway` | 8100 | 9100 |
| `mars-cloud-auth-service` | 8101 | 9101 |
| `mars-cloud-upms-service` | 8102 | 9102 |
| `mars-cloud-sample-service` | 8103 | 9103 |
| 业务服务 | 8104–8179 | 9104–9179 |
| `mars-cloud-monitor` | 8190 | 9190 |

约定由可观测性组件实现：端口从业务端口推导，不逐服务配置；显式配置与约定不符时启动失败。
管理端口只对内网开放；`health` 允许匿名读取，其余端点需要 Basic 认证，凭据由部署时的环境变量提供。

业务端口的上界 8179 就是为这条推导留的：它把两段端口都圈在 8100–8199 与 9100–9199 之内，
新建服务只要落在 8104 到 8179，管理端口必然不与本表其他行、也不与本地中间件栈的端口重叠。
超出这个范围新建部署物时，要先确认业务端口与业务端口加 1000 两个值都没有被占用。

## 两条不可越过的边界

### 认证与授权不合并

认证回答「你是谁」，授权回答「你能干什么」。两者是两个服务、两套模型，
合并会同时放大故障域与权限模型的复杂度。

### 登录渠道返回的组织与角色不参与鉴权

第三方渠道在免登时会顺带返回部门与角色。这些信息**只用于身份确认**，
必须映射进授权服务的主体模型后由 PDP 统一判定，不能直接当成权限事实来源——
否则会分裂出两套权限模型。

## 令牌里不放权限清单

令牌只承载身份。权限每次向授权服务实时查询，这样：

- 改一个用户的权限立即生效，不用等令牌过期
- 权限判定始终有唯一事实来源

即使将来更换认证实现，验证侧也只需改一行 issuer 配置。

## 服务间调用

服务之间的调用**绕过网关**，因此每个服务都要自己完成鉴权，网关只是第一道。
Servlet 服务的同步读调用使用 `mars-cloud-feign-spring-boot-starter`：调用方只写服务名，
由 Nacos 与 LoadBalancer 选实例；调用方身份与租户由框架统一传播。应用提供
Tracer 与 ObservationRegistry 时，Micrometer 自动传播 W3C `traceparent`。
下游失败必须翻译为调用方自己的错误码，不透传下游 message 或原始响应体。

Feign 自身不重试。LoadBalancer 只允许 GET 换下一实例重试一次，POST 等写请求不重试。
响应式服务不使用 Feign，改用由 `WebClient` 驱动的 Spring HTTP Service Client。
